# Architecture

Carbon Commander is a Manifest V3 Chrome extension with three parts: a tiny content script, the bar
UI (an extension page shown in an iframe), and the service worker, which owns everything else.

```
┌ web page ─────────────────────────────┐      ┌ extension origin ───────────────────────┐
│ content script (tiny)                 │      │ service worker (background)             │
│  - hosts <iframe src=bar.html>        │      │  - agent sessions (per tab, Map)        │
│    in a closed shadow root            │      │  - LLM client (OpenAI-compatible)       │
│  - toggle / resize / Esc              │      │  - tool sources: built-in + MCP         │
│  - no app logic, holds no secrets     │      │  - chrome.scripting for page tools      │
│                                       │      │  - settings; secrets in IndexedDB       │
│ ┌ iframe: bar.html (extension origin)┐│◄────►│                                         │
│ │ command bar UI, chat, settings     ││ port │                                         │
│ └────────────────────────────────────┘│      └─────────────────────────────────────────┘
└───────────────────────────────────────┘
```

## Source layout

```
src/
  shared/       contracts: types.ts, protocol.ts (wire messages), defaults.ts, logger.ts
  background/   index.ts (entry + routing), sessions.ts, settings.ts, secrets.ts, bar-trust.ts
  llm/          client.ts (chat completions + SSE), providers.ts, tool-schema.ts
  agent/        loop.ts (pure agent loop), transcript.ts
  mcp/          client.ts (Streamable HTTP), manager.ts (servers -> one ToolSource),
                oauth.ts (OAuth protocol pieces), auth.ts (per-server sign-in state),
                discovery.ts (MCP servers advertised by visited sites)
  webmcp/       page tools: page-api.ts (MAIN-world document.modelContext, bundled as webmcp.js),
                page-functions.ts (injected list/call/abort), sanitize.ts, source.ts, register.ts
  tools/        registry, page executor, generic/ sites/ builtin/ toolsets (see tools/README.md)
  content/      index.ts, overlay.ts, keybind.ts
  ui/           bar.html, bar.ts, app.ts, chat/, settings/, state/, markdown.ts, styles/
  icons/        extension icons (generated by scripts/icons.mjs)
tests/          unit tests (Vitest) mirror src/; tests/e2e/ holds the Playwright tests
```

## Key decisions

1. **The UI lives in an extension-origin iframe** (`bar.html`) inside a closed shadow root, shown
   as a centred overlay in the browser's top layer. The page cannot read the UI, the conversation
   or any key. `bar.html` also works as a normal extension tab (`bar.html?tabId=N`), which is the
   fallback for pages that cannot be scripted (`chrome://`, the Web Store, the PDF viewer).
   - Stacking: the overlay host is a manual popover. When the page has a modal `<dialog>` open
     (which would make a popover inert), the overlay opens its own `<dialog>` with `showModal()` so
     it stacks above the page's modal. In that mode the page, including its dialog, is inert for
     the user while the bar is open; page tools still work (scripted clicks and events are not
     blocked by inertness), but nothing on the page can take focus until the bar is closed.
   - The host is attached to `<html>`, so pages that swap `<body>` (Turbo-style navigation) keep
     it; if the host was removed anyway, opening the bar re-attaches it with a fresh iframe.
2. **The agent loop runs in the service worker**, one session per tab id. The session (UI
   transcript + model messages) is written to `chrome.storage.session` after every step, so a worker
   restart or a page navigation (which destroys the iframe) can re-attach and replay. A run that
   was in flight when the worker stopped is closed with an "interrupted" note. Every run has an
   `AbortController` and a step limit. While any run is active the worker calls a cheap extension
   API every 20 s (an extension API call resets Chrome's idle timer) and an attached UI pings it
   over its port, so a run is not cut off as idle. When a tab closes, attached UIs get
   `run.error { code: 'no-tab' }` and show that the tab is gone.
3. **Page tools run via `chrome.scripting.executeScript`** straight from the worker (ISOLATED
   world by default, MAIN only where a tool declares it). The tab context (URL, title) is refreshed
   before every agent step, so URL-matched toolsets and the system prompt follow navigations.
4. **One LLM client** for the OpenAI-compatible chat-completions API with streaming and tool calls.
   Providers are OpenRouter, Ollama (`http://localhost:11434/v1`) and a custom base URL. Models are
   chosen per role (`chat`, `vision`, `autocomplete`) from the provider's `/models` list. When the
   provider says the chat model does not accept images (`supportsImages === false`), images from
   tools (screenshots, MCP images) are described by the `vision` model and passed on as text; without
   a usable vision model the chat model gets a note that the image could not be shown. Reasoning
   models on OpenRouter show a "thinking…" state, and their `reasoning_details` are sent back on
   tool-call turns (OpenRouter only). Default model ids live only in `src/shared/defaults.ts`.
5. **Real MCP over Streamable HTTP**, both protocol eras of the 2026-07-28 revision:
   - *modern* (2026-07-28, stateless): `server/discover`, then `tools/list` / `tools/call` with the
     protocol `_meta` and the mirrored `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name` and
     `Mcp-Param-*` headers; no session, no `ping`; a response stream that breaks is re-issued once
     as a new request; `ttlMs` caches the tool list (0 counts as the 30 s minimum);
   - *legacy* (2025-11-25, 2025-06-18, 2025-03-26): `initialize` + `notifications/initialized`,
     `Mcp-Session-Id`, resumable SSE streams (the server's `retry` is respected up to 30 s),
     `notifications/cancelled`.

   `connect()` tries `server/discover` first and falls back to `initialize` when the server does
   not answer as a modern server (or lists only legacy versions). A server that answers
   `initialize` with `2024-11-05` (old SDKs serving Streamable HTTP) is accepted; that version is
   never offered. Bearer token / custom headers per server, stored encrypted, or OAuth (below). MCP
   tools are exposed to the model as `mcp__<server>__<tool>`.
6. **One tool definition format and one registry** (`ToolDefinition`, `ToolSource`). The agent
   loop only sees `ToolSource[]`: the built-in registry, the MCP manager and the WebMCP source.
7. **Model output is always sanitised** (marked, then DOMPurify) before it touches the DOM. Tool
   output is rendered as text, never HTML.
8. **Page tools (WebMCP)** follow the WebMCP draft of 2026-11-13 (`document.modelContext`:
   `registerTool(tool, { signal })`, `getTools()`, `executeTool(tool, input, { signal })`,
   `toolchange`).
   - *Providing the API.* While `Settings.webmcp` is on, the worker registers `webmcp.js` with
     `chrome.scripting.registerContentScripts` (MAIN world, `document_start`, top frame only);
     when it is off the script is unregistered, so Chrome injects nothing. A static manifest entry
     could not follow the setting: the script must decide before any page script runs and cannot
     read extension storage. The registration persists across restarts and updates and is
     reconciled with the setting on every worker start and settings change (a registration that
     differs from the current definition is replaced). The script does nothing when the browser
     has `document.modelContext` already (Chrome's native API, behind a flag / origin trial);
     otherwise it installs a small spec-shaped implementation (imperative API only).
   - *Compatibility shim.* Together with it (never over a native implementation, nor over a
     `navigator.modelContext` the browser already has), the script installs the shape of the
     earlier drafts and Chrome's early preview (spec text until March 2026):
     `navigator.modelContext.provideContext({ tools })` (replaces all tools, atomically),
     `clearContext()`, `registerTool(tool)`, `unregisterTool(name)` (synchronous, throwing), and
     tools called as `execute(input, client)` with `client.requestUserInteraction(cb)` (runs `cb`).
     It is a second view of the same tool set; results (strings or MCP-style
     `{ content: [...] }`) go through `executeTool`'s JSON serialisation and the worker unpacks them.
   - *Reading and running tools* is pull-only: the worker injects `listPageTools` / `callPageTool`
     (`chrome.scripting.executeScript`, MAIN world, top frame) and they use the API's own consumer
     methods `getTools()` / `executeTool()`, so native and provided implementations work the same
     way (native includes declarative form tools). There is no listener for the page anywhere in
     the extension.
   - The source is `dynamic`: the agent loop lists it again before every step (other sources are
     listed once per run and after navigations), so SPA re-registration is followed mid-run. Each
     listed tool carries `ToolSpec.binding` (the document id it was listed from), which the loop
     hands back as `ToolCallContext.binding`: the call goes to that document only.
9. **MCP OAuth** follows the Authorization section of the 2026-07-28 revision (`src/mcp/oauth.ts`
   for the protocol, `src/mcp/auth.ts` for the per-server state), hand-rolled with `fetch` and
   WebCrypto. It applies to servers without a saved token / headers:
   - *Discovery*: on a 401 the `WWW-Authenticate` Bearer challenge is kept (`resource_metadata`,
     `scope`). Sign-in fetches the protected resource metadata (the challenge's URL, then
     `/.well-known/oauth-protected-resource/<path>`, then the root form); its `resource` must be the
     server URL or a same-origin path prefix of it. The first listed authorization server whose
     metadata validates is used (RFC 8414 `oauth-authorization-server`, then OpenID discovery, with
     path insertion for path issuers); its `issuer` must equal the identifier the URL was built
     from, and `S256` must be in `code_challenge_methods_supported` (absent = refuse).
   - *Client id*: the one the user entered for that server (`McpServerConfig.oauthClientId`), else
     a stored dynamic registration for the same issuer and redirect URI, else RFC 7591 dynamic
     registration as a public client (`token_endpoint_auth_method: none`, `application_type: web`,
     redirect URI `https://<id>.chromiumapp.org/mcp-oauth`). Client ID metadata documents (the
     spec's preferred option) need an https URL the client controls, which an unpacked extension
     does not have. Without either, the error names the redirect URI to register manually.
   - *Plan, shown before any window*: once a server answers 401, the authorization server is found
     with read-only GETs and the server's status carries `oauth.plan`: the host the sign-in window
     opens (`authorization_endpoint`; flagged when it is on another site than the MCP server,
     approximated without the public suffix list) and the scopes, chosen per the spec's Scope
     Selection Strategy: the 401 challenge's `scope`, else the PRM's `scopes_supported`, else no
     `scope` parameter; step-up: the previously requested scopes plus the `insufficient_scope`
     challenge's (which cannot be left out). With more than one scope the user can uncheck some;
     what was left out is remembered per server (in the OAuth record). One click on "Sign in"
     sends `mcp.signIn` with `confirm: { authorizationHost, scopes }`; the worker reads the
     metadata again and refuses (before registering or opening anything) when the sign-in host is
     not the one shown or a scope is not offered. Adding a discovered server never opens a window.
   - *Authorization*: code + PKCE S256, random `state`, `resource` (RFC 8707: the PRM resource,
     canonical form) and the confirmed scopes, in
     `chrome.identity.launchWebAuthFlow({ interactive: true })` from the worker. The response is
     checked in order: `iss` (RFC 9207; required when the server advertises it; a mismatch rejects
     the response without using its `error`), `state`, `error`, `code`. Then the token exchange
     (with `code_verifier`, `redirect_uri`, `resource`); only `Bearer` tokens are accepted.
   - *Storage*: one JSON record per server (client registration, issuer, token / revocation
     endpoints, tokens with expiry and scope) in the encrypted secret store as `mcp-oauth-<id>`,
     a name no RPC accepts. It is bound to the server URL: changing the URL or client id revokes the
     tokens (best effort, with the old URL's record) and drops the record.
   - *Use*: the client asks for the token before each request and sends it only to the MCP server
     URL. It is refreshed when it expires within 60 s, and on a 401 once (single-flight per server:
     concurrent requests wait for the same refresh), then the request is retried once.
     `invalid_grant` drops the tokens ("sign-in required"); `invalid_client` / `unauthorized_client`
     (from the token endpoint or the authorization response) also drops a dynamic registration,
     so the next sign-in registers again instead of failing forever. A generation counter per
     server discards a refresh that finishes after a sign-out, a new sign-in or a URL change, so it
     cannot bring old tokens back. A 403 `insufficient_scope` is recorded and the UI offers "Sign in
     again" (with its plan).
   - *Never automatic*: the agent never starts a sign-in. A tool call on a server that needs one
     returns an error telling the model to ask the user to sign in from Settings → MCP; a server
     that needs sign-in lists no tools. Interactive sign-in is only the `mcp.signIn` RPC from the
     settings UI.
   - *Worker restarts*: the PKCE verifier and `state` live only in memory. A sign-in in progress is
     marked (no secrets) in `chrome.storage.session`; a worker that starts and finds a marker it did
     not set reports "sign-in interrupted" and the user starts again. The worker is kept alive while
     the window is open, and the interactive step gives up after 10 minutes.
   - *Sign out* revokes the refresh and access tokens (RFC 7009) when the server has a revocation
     endpoint, then deletes them; the client registration is kept for the next sign-in.
10. **MCP discovery** (`src/mcp/discovery.ts`): on `chrome.tabs.onUpdated` (`status: complete`),
    the page's origin is checked when the setting is on, the tab is not incognito and the page is
    `https://` (or `http://localhost`): `GET /.well-known/ai-catalog.json` (the AI Catalog that
    SEP-2127 server cards are discovered through, per `modelcontextprotocol/experimental-ext-server-card`
    `docs/discovery.md`) and `GET /.well-known/oauth-protected-resource` (RFC 9728). Catalog entries
    of type `application/mcp-server-card+json` give the card inline (`data`) or by `url`: a card on
    the page's origin is fetched (`Accept: application/mcp-server-card+json`); one on another host
    is not (that would tell a third party which site was visited) and, when it is at the reserved
    location `<endpoint>/server-card`, lists that endpoint as a different host (all `source:
    catalog`). Only when the catalog is absent, unauthorised or names no MCP card,
    `GET /.well-known/mcp/server-card.json` (the earlier proposal's location, still served by some
    sites; `source: server-card`). Both card shapes are read (server.json-style `remotes`, older
    `serverInfo` + `transport`). So per checked origin: at most three well-known GETs, at most two
    same-origin cards named by the catalog, and one probe per same-origin endpoint found. A
    same-origin endpoint gets one unauthenticated `server/discover` POST (no session): a JSON-RPC
    answer means MCP, a 401 with a `resource_metadata` challenge means MCP behind OAuth; an
    endpoint the site's protected resource metadata names is marked as needing sign-in even when
    discovery itself is public. The POST carries `Origin: chrome-extension://<id>` (Chrome adds it)
    and `clientInfo`, so a site that advertises MCP learns the extension is installed; the GETs
    carry neither, nor cookies or a referrer. Not used: HTTP `Link` headers
    (`rel="describedby"`), which need `webRequest` and would wake the worker on every response; `<link>` elements (no MCP convention yet); the RFC 9727 `api-catalog`, which has no
    MCP relation and would cost a third request on every site.
    - *Limits*: one check per origin per browser session and day (checked origins in
      `chrome.storage.session`, at most 1,000), two sites at a time, 16 queued, 5 s timeouts, 64 KB
      per document, no cookies, no redirects, at most two cards per site. Requests go only to the
      page's origin; an endpoint on another host is listed with that host but not probed; a
      private / loopback endpoint named by a public site is dropped. At most 10 new servers are
      listed per hour (the rest are tried again on a later visit), so a site cycling through
      subdomains cannot push real entries out of the list.
    - *Storage*: up to 50 discovered servers (newest first, dropped after 30 days unseen) and the
      dismissed keys in `chrome.storage.local` (`cc_mcp_discovered`; restricted to trusted contexts
      where Chrome supports it, see the start of `background/index.ts`). This list (the origins it
      was found on, with dates) is the only trace of browsing it keeps; the checked origins live in
      `chrome.storage.session`. Names and descriptions are cleaned (control, invisible and bidi
      characters) and capped; endpoints pass the MCP URL rules. A site's name is shown as its claim,
      and becomes the server's config name (and so its tool names) only when it matches the
      endpoint's host; otherwise the host gives the name. Nothing is added automatically:
      `mcp.discovered.add` adds with that unique name; when the server needs sign-in, its row then
      shows the sign-in plan and the user clicks "Sign in". The bar shows "MCP server available"
      for the current tab's site (`mcp.discovered.forTab`).

## Channels

| Channel | Direction | What |
|---------|-----------|------|
| Port `bar` (`chrome.runtime.connect`) | bar ↔ worker | `session.attach`, `run.start`, `run.abort`, `confirm.reply`, `session.clear`, `ping`; replies `session.state` (full replay), `run.started`, `assistant.delta`, `assistant.thinking`, `tool.*`, `confirm.*`, `run.end`, `run.error`, `settings.changed` |
| RPC (`chrome.runtime.sendMessage({ rpc, params })`) | bar → worker | settings, secrets (`set/has/delete`, never `get`), providers, models, `mcp.*` (incl. `mcp.signIn` / `mcp.signOut`, `mcp.discovered.*`), `tools.list`, `autocomplete` |
| `chrome.runtime.sendMessage` | content script → worker | `bar.token` (handshake), `keybind.get` (the fallback shortcut) |
| `chrome.tabs.sendMessage` | worker → content script | `overlay.toggle/open/close`, `overlay.suspend/resume` (hidden during screenshots), `keybind` (pushed when it changes) |
| `chrome.scripting.executeScript` (MAIN world) | worker → page → worker | WebMCP: list the page's tools, run one, abort one (`webmcp.status` RPC feeds the bar's chip). Only the return value of a script the worker started comes back; the page cannot initiate anything |
| `MessageChannel` port | bar ↔ content script | `close`, `resize`, `raise` (bar → host); `shown`, `hidden` (host → bar). The port is handed to the bar in the `init` message (target origin pinned to the extension); nothing is posted to the page's window |

All message shapes are typed in `src/shared/protocol.ts`; the worker validates everything it
receives. While the port is reconnecting, the bar refuses to send a new message (the text stays in
the input) and queues control messages (abort, confirmation replies, clear) in order.

### Usage accounting

The worker adds a run's token usage to the session total when the run ends, and `run.end` carries
that run's usage. A UI adds `run.end.usage` to the total it got from its last `session.state`.
Because a `session.state` sent mid-run does not yet include the running run, nothing is counted
twice (covered by a test in `tests/background/sessions.test.ts`).

## Security model

### Isolation from the page

- The bar is an extension page in a closed shadow root; the page sees an empty custom element.
- The bar never posts to the page's window. Its only link to the content script is a private
  `MessageChannel` port, handed over in an `init` message whose target origin is pinned to the
  extension. So the page gets no message, no `event.source` (a reference to the bar's window) and
  no notice of resizes from the bar. It can still see the host element appear and disappear.
- A load of the bar iframe that the content script did not start (something navigated it) is
  treated as hostile: the iframe is destroyed and a fresh one is created (new handshake).
- Key handlers in the content script ignore synthetic events (`isTrusted === false`), so a page
  cannot open or close the overlay by dispatching key events.

### Frame ownership

`bar.html` must be web-accessible to be framed, so:

- it is declared with `use_dynamic_url: true`: pages can only load it through a per-session URL
  that only the content script knows (`chrome.runtime.getURL`);
- an embedded bar must prove it is in the iframe our content script created. On every iframe load
  the content script registers a random single-use token with the worker, bound to its tab, and
  posts it to that iframe only. The bar claims the token; the worker then trusts that bar document
  (`sender.documentId`). Ports and RPCs from any other framed bar document are refused, and such a
  bar shows a refusal message instead of the UI. Top-level extension pages (the bar opened as a
  tab) are trusted.
- A page that frames `bar.html` itself (if the dynamic URL leaked) can post fake `init` messages
  to it; they fail to claim (the bar allows a few attempts) and the bar refuses to start.

### Confirmations

When **Ask before tools change things** is on (the default), the user approves each call of:

- tools marked `mutates` (click, type, navigate, open a tab, ...);
- tools marked `egress`, which send a request to a host the model chooses: `fetch_url`. The prompt
  names the destination host ("sends a request to example.com");
- calls that set an argument listed in `confirmWhenArgs`: `list_tabs` with `all_windows`;
- every MCP tool, unless the user enabled **Trust read-only hints** for that server (then tools the
  server marks `readOnlyHint: true` run without asking);
- every page tool (WebMCP, `ToolSpec.pageTool`), whatever the page claims (`readOnlyHint` is
  ignored: the page that declares the tool is the untrusted party). The prompt names the page's
  host as the source ("Page: example.com") and says the page, not the extension, decides what the
  tool does.

With the setting off, none of these ask, MCP and page tools included.

"Always allow" applies to that tool on the origin of the tab at the time it was granted, for the
rest of the conversation; on another origin the tool asks again. It is cleared with the
conversation.

The prompt resists accidental and tricked approvals:

- its buttons ignore activation for 500 ms after it appears (and after the overlay is shown
  again);
- it never takes focus from the message box while the user is typing; it is announced instead,
  and Shift+Tab from the message box reaches its buttons (Deny first). There are no single-letter
  shortcuts;
- in a page, its buttons accept a click only while Chrome's occlusion check
  (`IntersectionObserver` with `trackVisibility`, built for detecting clickjacking in cross-origin
  iframes) reports them visible: unobscured, not made transparent and not distorted. This catches a page element drawn
  over the prompt even when it lets clicks pass through (`pointer-events: none`). The check may
  report "not visible" when it is, never the opposite (in which case the prompt says so and the user
  can try again). When a prompt appears the bar also asks the content script to move the overlay
  back to the top of the top layer.

**What confirmations do not cover.** They gate actions and requests to model-chosen hosts. They
do not stop data from reaching:

- the model provider: page text, tool results and earlier tool output stay in the conversation and
  are sent with every request. They stay in context when the tab navigates to another site (a
  later page can see, through the model, what an earlier page or tool returned);
- the fixed API hosts of the site toolsets, which take model-chosen queries and paths without
  asking: `hn_*` (on news.ycombinator.com; Hacker News' Firebase API and Algolia's HN search) and
  `github_*` (on github.com; GitHub's REST API). The model cannot choose another host through them,
  but it can put text into those requests;
- an approved request: once you allow `fetch_url` or a navigation, whatever the model put in the
  URL goes with it. Read the arguments in the prompt.

Model output cannot load remote content in the bar: the bar's content security policy allows
images only from the extension, `data:` and `blob:`, and links open only when clicked.

### Untrusted content

Page text, tool results, MCP output and the page title / address go to the model as data; the
title and address are placed in a block labelled as untrusted page data, with control characters
removed and length capped (200 / 500 characters). The system prompt tells the model not to follow
instructions found in them. This reduces but does not remove prompt-injection risk; confirmations
are the backstop.

### Page tools (WebMCP)

The page is the untrusted party: it declares the tools, writes their descriptions and schemas, and
produces their results. So:

- **No channel from the page.** The worker pulls (see key decision 8): it injects a function, and
  only that function's return value comes back. No content script, port or `onMessage` listener
  accepts anything from the page, and the manifest has no `externally_connectable`, so a page has
  no `chrome.runtime` to message the extension with. A page can replace `document.modelContext`
  or patch built-ins, but that only changes what *it* offers; everything returned is validated in
  the worker. The provided API exposes only the draft's interface (no extension handle); the only
  extension-made global is a page-visible map of running calls' `AbortController`s
  (`Symbol.for('carbon-commander.webmcp.calls')`), which lets a page abort only its own tools.
- **Validation and caps** (`src/webmcp/sanitize.ts`): names must match the draft's
  `[A-Za-z0-9_.-]{1,128}`; at most 32 tools per page, 128 entries looked at; descriptions 3 000
  characters, titles 200; input schemas must be JSON objects with `type` `object` (or none), at
  most 16 KB and 32 levels deep; descriptions + schemas of one page at most 64 KB; results 32 000
  characters with a truncation marker that says how long the result was; error messages 1 000.
  Control characters (C0/C1) and bidi / zero-width controls are removed. Invalid or excess tools are
  dropped.
- **No shadowing.** Page tools are exposed as `webmcp__<name>` (sanitised to the model's name rule,
  hash suffix on collisions or length), and the WebMCP source comes last (the first source to
  expose a name wins). The model-facing description starts with a note naming the page's host and
  saying the text is untrusted.
- **Pinned to the document.** A call targets the document the model saw the tool in (the listing's
  `ToolSpec.binding`, Chrome's `documentId`), not the tab's latest listing (the bar's chip and the
  settings' tool list read the tab again), and checks the page's origin again in the page, so a
  call never reaches a page the tool was not listed from, even a same-site page offering a tool of
  the same name: after a navigation it fails and the next step lists the new page's tools. The
  source label uses the page's own `location.origin`.
- **Bounded.** Listing gives up after 3 s, a call after 60 s; on timeout or Stop the worker aborts
  the call in the page (the tool's `AbortSignal`). A page that never answers costs the agent that
  time, nothing more. Page tool output is rendered as text, never HTML.
- **Fingerprinting.** In browsers without native WebMCP, the provided `document.modelContext`
  (and the `navigator.modelContext` compatibility shim) tells every page that the extension (or
  another WebMCP provider) is installed. The setting turns this off.

### Network

- `fetch_url` sends no cookies, asks first (see above) and does not follow redirects (the request
  would reach the redirect target before its address could be checked; the model is told to fetch
  the final URL instead). It refuses, by host name: `localhost` and `*.localhost`; private, loopback,
  link-local, CGNAT, multicast and reserved IPv4 literals in any notation the URL parser accepts;
  loopback, unspecified, IPv4-mapped, unique-local, link-local, multicast and NAT64 IPv6 literals;
  single-label and `.local` / `.lan` / `.internal`-style names; wildcard and loopback DNS services
  (`nip.io`, `sslip.io`, `xip.io`, `traefik.me`, `localtest.me`, `lvh.me`, `vcap.me`,
  `localhost.direct`); and names that embed a private IPv4 address (`10.1.2.3.example.com`,
  `10-1-2-3.example.com`). It cannot see DNS: any other public name that resolves to a private
  address (DNS rebinding, a custom wildcard domain) is not blocked.
- LLM providers and MCP servers must use `https://`; plain `http://` is accepted only for
  `localhost`, `127.0.0.1` and `[::1]`. Their requests carry the API key / token, so they do not
  follow redirects either (a clear error asks for the final URL).
- Responses are read with size caps (LLM streams 32 MB, one SSE event 8 MB, JSON 16 MB, site
  toolset APIs 4 MB, MCP responses 16 MB, OAuth and discovery documents 64 KB).
- OAuth endpoints and metadata URLs follow the same rule (`https://`, local `http://`), must not
  have a fragment, and must not be private / loopback hosts unless the MCP server is on one. OAuth
  requests send no cookies and do not follow redirects. Access tokens go only to the MCP server's
  URL, refresh tokens and codes only to the token endpoint, tokens being revoked only to the
  revocation endpoint. No token is logged, returned by an RPC or put into a session transcript.

### Storage

- **Secrets** (API keys, MCP auth, MCP OAuth records) are AES-GCM encrypted in the extension origin's IndexedDB, with
  a non-extractable `CryptoKey` kept in the same database. Web pages and content scripts cannot open
  that database, and the key's raw bytes cannot be exported by script. Only the worker decrypts
  secrets, to send each one to the provider or MCP server it belongs to; there is no RPC that
  returns a secret. This does not protect against code running inside the extension, or against
  someone who can read and decrypt the browser profile on disk. Older versions kept an extractable
  key next to the ciphertext in `chrome.storage.local`; those values are migrated on first use and
  the old key and ciphertexts are deleted.
- **Settings, input history** live in `chrome.storage.local`, **sessions** in
  `chrome.storage.session`. The worker restricts `chrome.storage.local` to extension pages and the
  worker (`setAccessLevel('TRUSTED_CONTEXTS')`), which Chrome supports for the `local` area since
  version 140; on older versions content scripts (which run in each page's renderer process) could
  read settings and input history there. The content script never reads storage: it gets the
  fallback shortcut from the worker. `chrome.storage.session` is restricted to trusted contexts by
  default.
